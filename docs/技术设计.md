## 1. 选型结论（能否实现需求）

**能实现 MVP：全量净值历史（从采集日起）+ 持仓账户上的追加/部分赎回 + 观测表。** 栈与数据源能力匹配如下。

| 选型 | 结论 | 说明 |
| --- | --- | --- |
| Vite + Vue 3 + pnpm | 可以 | 登录、总览、持仓账户、申赎、流水、详情。 |
| Go | 可以 | HTTP、定时采集、HTML 解析、流水还原与收益纯函数。 |
| SQLite | 可以（当前规模） | 百级用户、账户数千、全目录净值/观测百万行量级。不适合多机写。 |
| 每日拉中行全部分页 | 可以，且作为采集策略 | 见 §4。 |
| 观测表 `nav_observation` | **一期必做** | 见 §4.4。 |
| 追加 / 部分赎回 | **一期必做** | 见 §5–§6。银行页不能代替流水。 |

**数据源做不到、因而系统也做不到的事：**

1. 中行页只有各产品当前最新净值。每日全量 = 从第一次成功采集日起向前攒，不能回放更早历史。
2. 页面没有用户仓位。调仓必须记买入/赎回流水。
3. 某日采集失败且官网已跳到下一净值日，中间净值日可能缺失。缓解：一天多次采集 + `crawl_run` + 观测。

## 2. 系统形态

单体仓库；开发时 Vite 与 Go 两进程；生产可「一个 Go 二进制 + `web/dist`」。

```text
浏览器 (Vue SPA)
    │  HTTPS / 同源 Cookie
    ▼
Go HTTP API  ──┬── SQLite (WAL)
               └── 采集调度 (同一进程)
                      │
                      ▼
               中行静态 HTML /sourcedb/srfd6_2024/
```

- 时区：`Asia/Shanghai`。
- 认证：HttpOnly + SameSite=Lax 的服务端 Session（token 存 SQLite）。仅 HTTPS（含 `X-Forwarded-Proto: https`）或 `COOKIE_SECURE=true` 时加 Secure；HTTP 直连不加，否则浏览器不保存 Cookie。
- 合规文案：前端固定「收益估算，以发行机构/代销机构结算为准」。

### 2.1 推荐目录

```text
money-tacker/
  docs/
  web/
  cmd/server/main.go
  internal/
    http/
    auth/
    user/
    product/
    holding/              # 持仓账户 + 流水写入/作废
    pnl/                  # 由流水+净值还原份额/成本/当日收益（无 IO 纯函数优先）
    nav/
    crawl/
    db/
  migrations/
  data/
```

Go 模块名：`money-tacker`。前端**仅 pnpm**。

## 4. 采集：每日全量 + 观测

### 4.1 策略

每个自然日全量扫描 `index.html` … 直至空页/404。调度（可配）：上海 `10:00 / 16:00 / 21:00`，进程启动补一次。页间 300～800ms，worker = 1。

### 4.2–4.3 礼貌与解析

与 v0.1 相同：列名解析、净值日=截止日期、字段可空进 `extra_json`。`User-Agent` 标明工具名。失败指数退避，debug HTML 仅保留最近失败页。

### 4.4 两层历史（观测表一期必留）

| 层 | 表 | 作用 |
| --- | --- | --- |
| 业务净值 | `nav_snapshot` | `PRIMARY KEY (product_code, nav_date)`。收益只读此表。 |
| 观测 | `nav_observation` | 每次**成功扫到该产品**写一行：`crawl_run_id + product_code` + 当时页面上的净值日与单位净值。净值日未变也写。 |
| 任务 | `crawl_run` | 起止、页数、产品数、`success\|partial\|fail`。 |

`partial`：部分页失败。已成功页的产品仍写观测；失败页不编造观测。

产品 upsert：`listed` 连续多日未见则置 0，不删快照与观测。

### 4.5 与调仓

全量采集解决目录与净值；**换仓 = 赎回 A 的流水 + 买入 B 的流水**。B 的净值序列从系统上线日已在库中，不必等用户第一次点追加才开始记。

## 5. 数据模型

### 5.1 ER

```text
user 1──* holding *──1 product
holding 1──* ledger_entry
product 1──* nav_snapshot
crawl_run 1──* nav_observation *──1 product
user 1──* session
```

`UNIQUE(user_id, product_code)` 保证一本账。收益与剩余份额**不落库**。

### 5.2 表结构

```sql
CREATE TABLE user (
  id            INTEGER PRIMARY KEY,
  account       TEXT NOT NULL UNIQUE COLLATE NOCASE,
  password_hash TEXT NOT NULL,
  created_at    TEXT NOT NULL
);

CREATE TABLE session (
  token      TEXT PRIMARY KEY,
  user_id    INTEGER NOT NULL REFERENCES user(id),
  expires_at TEXT NOT NULL
);

CREATE TABLE product (
  code           TEXT PRIMARY KEY,
  name           TEXT NOT NULL,
  issuer         TEXT,
  last_seen_page INTEGER,
  last_seen_at   TEXT,
  listed         INTEGER NOT NULL DEFAULT 1,
  updated_at     TEXT NOT NULL
);

CREATE TABLE nav_snapshot (
  product_code      TEXT NOT NULL REFERENCES product(code),
  nav_date          TEXT NOT NULL,
  unit_nav          INTEGER,
  acc_nav           INTEGER,
  daily_return_bp   INTEGER,
  extra_json        TEXT,
  fetched_at        TEXT NOT NULL,
  PRIMARY KEY (product_code, nav_date)
);

CREATE TABLE crawl_run (
  id            INTEGER PRIMARY KEY,
  started_at    TEXT NOT NULL,
  finished_at   TEXT,
  status        TEXT NOT NULL,
  pages_ok      INTEGER NOT NULL DEFAULT 0,
  products_ok   INTEGER NOT NULL DEFAULT 0,
  error_summary TEXT
);

CREATE TABLE nav_observation (
  crawl_run_id INTEGER NOT NULL REFERENCES crawl_run(id),
  product_code TEXT NOT NULL REFERENCES product(code),
  nav_date     TEXT NOT NULL,
  unit_nav     INTEGER,
  PRIMARY KEY (crawl_run_id, product_code)
);

CREATE INDEX idx_obs_code_date ON nav_observation(product_code, nav_date);

CREATE TABLE holding (
  id           INTEGER PRIMARY KEY,
  user_id      INTEGER NOT NULL REFERENCES user(id),
  product_code TEXT NOT NULL REFERENCES product(code),
  created_at   TEXT NOT NULL,
  UNIQUE (user_id, product_code)
);

CREATE TABLE ledger_entry (
  id             INTEGER PRIMARY KEY,
  holding_id     INTEGER NOT NULL REFERENCES holding(id) ON DELETE CASCADE,
  kind           TEXT NOT NULL,          -- buy | redeem
  occur_date     TEXT NOT NULL,          -- YYYY-MM-DD
  cash_fen       INTEGER NOT NULL,       -- 买入付出或赎回收回，恒 ≥ 0
  shares_e8      INTEGER NOT NULL,       -- 份额绝对值，恒 ≥ 0
  unit_nav_e8    INTEGER NOT NULL,
  nav_date_used  TEXT NOT NULL,
  voided_at      TEXT,                   -- NULL=有效
  note           TEXT,
  created_at     TEXT NOT NULL
);

CREATE INDEX idx_ledger_holding ON ledger_entry(holding_id, occur_date, id);
```

同一天多笔：还原顺序为 `occur_date ASC, id ASC`（写入顺序）。用户应按真实先后录入。

作废：只能把该 `holding_id` 下 `voided_at IS NULL` 且 `id` 最大的一行打上 `voided_at`。作废后剩余份额用其余有效流水重算，必须 ≥ 0（因只作废最后一笔，自然满足，除非数据被手工改库）。

### 5.3 精度

| 量 | 存储 | 展示 |
| --- | --- | --- |
| 金额 | 分 | 元，2 位 |
| 净值 | ×10⁸ | 至少 4 位 |
| 份额 | ×10⁸ | 4～6 位 |
| 收益率 | 计算后 round | 百分比 2 位 |

主路径禁止 IEEE 浮点。夹具：`10000 / 1.0562`；再加「买 10000 再赎回一半」的成本摊销。

赎回按金额：`shares = floor_or_round(cash / nav)` 与实现约定写死一种并单测；**全部赎回**用剩余份额，赎回金额 = 剩余份额 × 赎回净值，避免尾差留灰渣份额。

## 6. 领域规则（`internal/pnl`）

展示日 D 默认今天；`DISPLAY_LAG_DAYS` 默认 0。

解析净值：发生日 T 的所用净值 = `nav_date = T` 的 `unit_nav`，否则 T 之前最近一条；再无则要求请求带手工净值，否则 `NAV_UNAVAILABLE`。

### 6.1 还原账户状态

按有效流水顺序：

```text
剩余份额、剩余成本 初始 0
已实现、累计买入金额、累计赎回金额 初始 0

buy:    剩余份额 += shares; 剩余成本 += cash; 累计买入 += cash
redeem: 若 shares > 剩余份额 → 拒绝（写入时即拒绝）
        摊销 = 剩余成本 * shares / 剩余份额     -- 整数除法规则见实现：先乘后除
        已实现 += cash - 摊销
        剩余份额 -= shares; 剩余成本 -= 摊销
        累计赎回 += cash
```

清仓后剩余份额与剩余成本均为 0（摊销应吃干净；最后一笔全部赎回用「剩余份额」而不是金额反推，保证成本清零）。

```text
最新市值   = 剩余份额 × 最新单位净值
未实现     = 最新市值 - 剩余成本
累计收益   = 未实现 + 已实现
           = 最新市值 + 累计赎回 - 累计买入
累计收益率 = 累计收益 / 累计买入     （分母 0 不展示）
持仓收益率 = 未实现 / 剩余成本       （剩余成本 0 不展示）
```

### 6.2 当日收益

`shares_sod(D)` = 仅用 `occur_date < D` 的有效流水还原出的剩余份额。

```text
无 NAV_D → 0
有 NAV_D →
  hold = shares_sod * (NAV_D - NAV_prev)   // 无 NAV_prev 则 hold=0
  buyD = Σ 当日有效买入 shares * (NAV_D - 该笔 unit_nav)
  当日收益 = hold + buyD
```

挂零日即使有申赎，当日收益仍为 0。

### 6.3 写入规则

1. 首次买入：产品须能解析到；创建 `holding` + `buy` 同一事务。`PRODUCT_NOT_FOUND` 则全滚。
2. 追加：账户必须已存在（或视为首次买入同一接口：不存在则创建）。
3. 赎回：账户必须存在且有效剩余足够。`INSUFFICIENT_SHARES`。
4. 产品查找：先本地 `product`；没有再同步全量扫描，接口超时 60s。
5. 删除账户：`DELETE holding` 级联流水，不删净值。

现金管理类：有流水也只展示 extra 原始字段，不把每万份当 NAV。

## 9. 实现顺序

| 阶段 | 产出 |
| --- | --- |
| M1 | 迁移 + 用户会话 + holding/ledger 写入校验 + 作废最后一笔 |
| M2 | 全量 crawl + snapshot/observation；`pnl` 纯函数单测（挂零、追加、部分赎回、清仓） |
| M3 | Vue 申赎与列表；验收 1–10 |
| M4 | 采集重试、partial、文案 |

**必须有的测试：**

- HTML fixture：`AF247494G` 截止日期与单位净值。
- upsert 净值不重复行；同一产品两次观测属于不同 `crawl_run`。
- 挂零日收益 0；有 NAV_D 后重算。
- 买 10000 再赎一半：已实现、剩余成本、累计收益恒等式。
- 超额赎回失败；作废非最后一笔失败。
- 两用户交叉不可见。
